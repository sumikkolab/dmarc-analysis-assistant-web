こんな課題を解決します

DMARC レポートの XML をどう読めばいいか分からないとき

DMARC 集約レポート（ZIP / GZ / XML）を取り込むと、送信元 IP・SPF/DKIM の結果・件数を読み取り、6 分類に自動で振り分けます。XML を直接読まなくても、対応すべきものと対応不要なものを区別できます。

SPF/DKIM が fail した送信元がなりすましか調べたいとき

DMARC が fail し、設定に登録した自社メールサーバーにも既知の送信サービスにも一致せず、転送の手掛かりも無い送信元を「なりすまし疑い」として表示します。対応の目安は「早期対応」です。詳細画面では、送信元 IP、該当メール数、SPF / DKIM の結果とドメイン一致の有無を確認できます。

自社メールが DMARC に失敗する原因を知りたいとき

設定画面に自社メールサーバーとして登録した IP から送られ、DMARC が fail したものを「設定不備」に分類します。対応の目安は「今週中に対応」です。送信元 IP のサーバーを特定し、SPF レコードに IP を追加するか DKIM 署名を有効にする手順が表示されます。

転送されたメールの DMARC fail を放置してよいか判断したいとき

レポートに転送やメーリングリストによる適用除外の理由（trusted_forwarder / mailing_list）が記録されたもの、または設定に登録した転送サーバーの IP 範囲から送られたものを「転送」に分類します。対応の目安は「対応不要」で、件数が急増した場合だけ転送経路を確認します。なお、SPF が fail でも DKIM が pass してドメインが一致していれば「正常」です。

DMARC ポリシーを p=reject に上げてよいか判断したいとき

本ツールは、ポリシーを上げてよいかどうかを判定しません。「なりすまし疑い」の詳細画面では、送信元 IP が自社や利用中の SaaS のものでないかを確認し、正当な送信元でなければ quarantine に変更し、問題がなければ reject へ段階的に移行する手順を示します。いきなり reject にしないよう注意も表示します。

送信元 IP が多く、どこから確認すべきか分からないとき

送信元サーバー別集計が、送信元 IP ごとにメール数・要確認件数・DMARC 成功率をまとめます。問題が多い送信元から順に確認できます。

見覚えのない送信元 IP が正規か確認したいとき

送信元サーバー画面の「設定照合」で、設定画面に登録した自社 IP・既知サービス・転送 IP との一致を確認できます。「登録なし」の行から、正規の送信元かどうかを確認します。自社の IP や転送サーバーを設定画面に登録すると、次の分析からその送信元の DMARC fail は「設定不備」や「転送」に分類されます。

複数ドメインを管理対象と監視対象に分けて整理したいとき

複数の受信ドメインをまとめて扱い、Managed / Monitored / External のタグを運用メモとして付けられます。組織としての DMARC の管理状況を整理して確認できます。

分析結果を CSV にして Excel で見たいとき

レコード一覧（20 列）と送信元サーバー一覧（22 列）を、UTF-8（BOM 付き）の CSV で出力できます。レコード一覧は、レコードごとの判定結果を Excel や BI ツールで詳しく分析するときに使います。送信元サーバー一覧は送信元 IP ごとの集計で、送信元 IP の確認をチーム内で分担するときに使います。列名はマニュアル第 5 章に掲載しています。

レポートを外部に出さずに解析したいとき

解析はローカル端末だけで行い、レポート本文・IP 情報・認証結果・ドメイン情報を外部サーバーに送信しません。Microsoft 365 からの取り込みは任意で、使用する権限は Mail.Read のみ（読み取り専用）です。

分類は一次トリアージの目安で、すべてを正確に分けるとは限りません。実際の被害の有無や攻撃者の意図は示しません。メールの送信・削除・編集と DNS の変更は行いません。

DMARC レポート、本当に読めていますか？

DMARC 集約レポート（RUA）は XML で届き、送信元 IP、認証結果（SPF/DKIM）、件数が並ぶだけ。パッと見ても「どれがなりすましで、どれが自社の設定不備で、どれが単なる転送なのか」が分かりません。

本ツールは、レポート本文をローカルで解析し、「対応すべきもの」と「放置してよいもの」を区別して表示します。

1 件ごとに表示される内容

レコードの詳細画面には、1 件ごとに結論・何が起きているか・具体的な対応の手順・対応の目安（早期対応 / 今週中に対応 / 対応不要）・判定の根拠が表示されます。根拠の欄では、送信元 IP、ドメイン、該当メール数、SPF / DKIM の結果とドメイン一致の有無、DMARC の結果を確認できます。手順の要点は次のとおりです。

なりすまし疑い（早期対応）

送信元 IP を確認し、自社や利用中の SaaS のものでないかを確かめます。正当な送信元でなければ DMARC ポリシーを quarantine に変更し、問題がなければ reject へ段階的に移行します。

設定不備（今週中に対応）

送信元 IP がどのサーバーかを特定し、サーバー管理者と共有します。SPF レコードに送信元 IP を追加するか、DKIM 署名を有効にします。サーバーを停止する必要はありません。

転送（対応不要）

転送やメーリングリストでは認証情報が変わることがあり、攻撃ではありません。件数が急増した場合だけ転送経路を確認します。転送メールをブロックすると、メーリングリストのメールが届かなくなります。

ダッシュボードで分かること

状態の 1 行
なりすまし疑いがあれば「外部から自社ドメインを装ったメールが検出されています」、設定不備があれば「自社メールサーバーの認証設定に不備が見つかっています」、どちらも無ければ「メールセキュリティは正常です。問題は検出されていません。」と表示されます。
次にやること
設定不備・なりすまし疑い・要確認があれば、それぞれの件数とともに、確認すべきことが表示されます。いずれも無ければ「現時点で対応が必要な項目はありません」と表示されます。
メール認証の成功率
「正常」に分類されたメール数 ÷ 全体のメール数。
なりすまし防御率
1 −（「なりすまし疑い」のメール数 ÷ 全体のメール数）。
送信元サーバー数
レポートに記録された送信元 IP の数。
ドメイン別サマリ
ドメインごとに、メール数・なりすまし疑い・DMARC 成功率を表で表示します。表示するドメインを 1 つ選ぶと、ダッシュボード全体をそのドメインに絞り込めます。

設定不備

転送

要確認

What it is
A Windows desktop app that analyzes DMARC aggregate reports (RUA) and bounce messages.
Who it is for
IT / operations staff at small to mid-sized organizations that own mail domains and need DMARC policy monitoring.
What it does
Imports ZIP / GZ / XML reports, classifies them into six categories (OK / Spoofing suspected / Config issue / Forwarded / Needs review / Read error), shows steps and a recommended timeframe for each entry, summarizes results by sending server and by domain, and exports CSV. Problems this solves

How do I read a DMARC aggregate report in XML?

Import DMARC aggregate reports (ZIP / GZ / XML) and the tool reads the source IPs, SPF/DKIM results, and counts, then sorts each entry into one of six categories. You can tell what needs action from what doesn't without reading the XML yourself.

How can I tell whether a sender failing SPF and DKIM is spoofing?

Entries that fail DMARC, match neither your registered mail servers nor a known sending service, and show no sign of forwarding appear as "Spoofing suspected", marked "Address promptly". The detail screen shows the source IP, the number of emails, and the SPF / DKIM results with whether each matched your domain.

Why does my own mail fail DMARC?

Mail that fails DMARC from an IP you registered in Settings as one of your own mail servers is classed as "Config issue", marked "Address this week". The app walks you through identifying the server behind the source IP and either adding that IP to your SPF record or enabling DKIM signing.

Does email forwarding cause DMARC to fail, and can I ignore it?

Entries are classed as "Forwarded" when the report records a forwarding or mailing-list override (trusted_forwarder / mailing_list), or when the source IP falls within a forwarding server range you registered in Settings. These are marked "No action needed"; check the forwarding path only if the count spikes. Note that mail failing SPF is still "OK" if DKIM passes and matches your domain.

Is it safe to move my DMARC policy to p=reject?

The app does not decide this for you. For "Spoofing suspected" entries, the detail screen guides you to confirm the source IP does not belong to your organization or a SaaS service you use, switch the policy to quarantine if the sender is not legitimate, and then move to reject gradually once no issues appear. It also warns against jumping straight to reject.

Which source IPs should I check first?

The sending server summary groups results by source IP, with mail volume, items needing attention, and DMARC pass rate. You can start with the sources that have the most problems.

Is an unfamiliar source IP legitimate?

The "server matching" column on the Sending Servers screen shows whether an IP matches the own IPs, known services, or forwarding IPs you registered in settings. Start with rows marked as not registered and confirm whether the sender is legitimate. Once you register your own IPs or forwarding servers in Settings, DMARC failures from those sources are classed as "Config issue" or "Forwarded" from the next analysis onward.

How do I organize DMARC across multiple domains?

Handle several receiving domains together and tag each one as Managed, Monitored, or External as an operational note. This keeps your organization's DMARC posture organized in one place.

Can I analyze DMARC results in Excel?

Export the record list (20 columns) and the sending server list (22 columns) as UTF-8 CSV with a BOM. Use the record list to analyze each record's result in detail in Excel or BI tools. Use the sending server list, which summarizes results by source IP, to split up the review of source IPs across your team. The column names are listed in Chapter 5 of the manual.

Can I analyze DMARC reports without uploading them anywhere?

Analysis runs only on your local device. Report contents, IP information, authentication results, and domain information are never sent to an external server. Microsoft 365 import is optional and uses the Mail.Read permission only (read-only).

Classification is a guide for first-pass triage and may not sort every entry correctly. It does not show whether harm occurred or what an attacker intended. The tool never sends, deletes, or edits mail, and never changes DNS.

Can you actually read your DMARC reports?

DMARC aggregate reports (RUA) arrive as XML — just source IPs, SPF/DKIM results, and counts. At a glance it's impossible to tell which rows are spoofing, which are your own misconfigurations, and which are harmless forwarded traffic.

This tool analyzes report contents locally and separates what needs action from what can be ignored.

What you see for each entry

The record detail screen shows, for each entry, a conclusion, what is happening, concrete steps, a recommended timeframe (Address promptly / Address this week / No action needed), and the evidence behind the result. The evidence includes the source IP, domain, number of emails, SPF / DKIM results with whether each matched your domain, and the DMARC result. Key steps by category:

Spoofing suspected (Address promptly)

Check the source IP and confirm it does not belong to your organization or a SaaS service you use. If the sender is not legitimate, change the DMARC policy to quarantine, then move gradually to reject once no issues appear.

Config issue (Address this week)

Identify which server the source IP belongs to and share the findings with its administrator. Add the IP to your SPF record or enable DKIM signing. There is no need to shut down the server.

Forwarded (No action needed)

Forwarding and mailing lists can alter authentication results; this is expected behavior, not an attack. Check the forwarding path only if the count spikes. Blocking forwarded mail would also drop mailing list messages.

Six classification labels

OK

SPF or DKIM passes and matches the sender domain. No action needed.

Spoofing suspected

Fails DMARC and matches none of your servers, known sending services, or forwarding. Address promptly.

Config issue

Fails DMARC from an IP registered as your own mail server. Address this week.

Forwarded

Fails DMARC with a forwarding or mailing-list record, or from a registered forwarding server. No action needed.

Needs review

Fails DMARC and matches a known sending service, but cannot be classified automatically. Review manually.

Read error

The report XML could not be read. Check the original attachment.

Classification is done by a rule-based engine. No AI inference or cloud analysis is used. See Chapter 4 of the manual for the detailed conditions.

Key features

DMARC aggregate report analysis

Supports ZIP / GZ / XML formats. Extracts source IP, authentication results, and counts, then classifies into six categories.

Bounce message analysis

Import bounce messages from Microsoft 365 or a local EML folder and sort them into four buckets: Confirmed bounce, Unmapped bounce, Detector flagged for review, and Normal mail (excluded). This is separate from the six DMARC report categories.

Sending server summary

Group results by source IP and review mail volume, items needing attention, DMARC pass rate, provider hints, and configured server matching.

CSV export

Export classification results to CSV for further analysis in Excel or BI tools, including SaaS sender attribution.
