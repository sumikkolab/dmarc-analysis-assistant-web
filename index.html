こんな課題を解決します

DMARC レポートの XML をどう読めばいいか分からないとき

DMARC 集約レポート（ZIP / GZ / XML）を取り込むと、送信元 IP・SPF/DKIM の結果・件数を読み取り、6 分類に自動で振り分けます。XML を直接読まなくても、対応すべきものと対応不要なものを区別できます。

SPF/DKIM が fail した送信元がなりすましか調べたいとき

SPF と DKIM がともに fail し、送信元 IP が自社管理外のものを「なりすまし疑い」として優先度高で表示します。送信元 IP と ASN を確認しながら、なりすまし送信の可能性を調査できます。

自社メールが DMARC に失敗する原因を知りたいとき

自社や正規 SaaS の送信元なのに SPF または DKIM が fail したものを「設定不備」に分類します。SPF レコードの include: / ip4: の漏れや、SaaS 側の DKIM 署名設定の抜けを確認する手掛かりになります。

転送されたメールの DMARC fail を放置してよいか判断したいとき

SPF が fail でも DKIM が pass のものや、転送に特徴的な中継 IP を経由したものを「転送由来」に分類します。通常は対応不要で、件数が異常に多い場合のみ確認します。

送信元 IP が多く、どこから確認すべきか分からないとき

送信元サーバー別集計が、送信元 IP ごとにメール数・要確認件数・DMARC 成功率をまとめます。問題が多い送信元から順に確認できます。

見覚えのない送信元 IP が正規か確認したいとき

送信元サーバー画面の「設定照合」で、設定画面に登録した自社 IP・既知サービス・転送 IP との一致を確認できます。「登録なし」の行から、正規の送信元かどうかを確認します。

複数ドメインを管理対象と監視対象に分けて整理したいとき

複数の受信ドメインをまとめて扱い、Managed / Monitored / External のタグを運用メモとして付けられます。組織としての DMARC の管理状況を整理して確認できます。

分析結果を CSV にして Excel で見たいとき

分類結果を CSV で出力でき、Excel や BI ツールでさらに分析できます。送信元 IP の確認をチーム内で分担したいときにも使えます。

レポートを外部に出さずに解析したいとき

解析はローカル端末だけで行い、レポート本文・IP 情報・認証結果・ドメイン情報を外部サーバーに送信しません。Microsoft 365 からの取り込みは任意で、使用する権限は Mail.Read のみ（読み取り専用）です。

分類は一次トリアージの目安で、すべてを正確に分けるとは限りません。実際の被害の有無や攻撃者の意図は示しません。メールの送信・削除・編集と DNS の変更は行いません。

DMARC レポート、本当に読めていますか？

DMARC 集約レポート（RUA）は XML で届き、送信元 IP、認証結果（SPF/DKIM）、件数が並ぶだけ。パッと見ても「どれがなりすましで、どれが自社の設定不備で、どれが単なる転送なのか」が分かりません。

本ツールは、レポート本文と関連するバウンスメールをローカルで解析し、「対応すべきもの」と「放置してよいもの」を区別して表示します。

Problems this solves

How do I read a DMARC aggregate report in XML?

Import DMARC aggregate reports (ZIP / GZ / XML) and the tool reads the source IPs, SPF/DKIM results, and counts, then sorts each entry into one of six categories. You can tell what needs action from what doesn't without reading the XML yourself.

How can I tell whether a sender failing SPF and DKIM is spoofing?

Entries where both SPF and DKIM fail and the source IP is outside your own infrastructure appear as "Spoofing suspected" with high priority. You can then check the source IP and ASN to investigate possible spoofed sending.

Why does my own mail fail DMARC?

Mail from your own or a legitimate SaaS source that fails SPF or DKIM is classed as "Config issue". It points you to gaps in the SPF record (include: / ip4:) and missing DKIM signing on the SaaS side.

Does email forwarding cause DMARC to fail, and can I ignore it?

Entries with SPF fail but DKIM pass, or routed through relay IPs typical of forwarding, are classed as "Forwarded". They usually need no action; check them only when the count is unusually high.

Which source IPs should I check first?

The sending server summary groups results by source IP, with mail volume, items needing attention, and DMARC pass rate. You can start with the sources that have the most problems.

Is an unfamiliar source IP legitimate?

The "server matching" column on the Sending Servers screen shows whether an IP matches the own IPs, known services, or forwarding IPs you registered in settings. Start with rows marked as not registered and confirm whether the sender is legitimate.

How do I organize DMARC across multiple domains?

Handle several receiving domains together and tag each one as Managed, Monitored, or External as an operational note. This keeps your organization's DMARC posture organized in one place.

Can I analyze DMARC results in Excel?

Export classification results to CSV and analyze them further in Excel or BI tools. It also helps when your team splits up the review of source IPs.

Can I analyze DMARC reports without uploading them anywhere?

Analysis runs only on your local device. Report contents, IP information, authentication results, and domain information are never sent to an external server. Microsoft 365 import is optional and uses the Mail.Read permission only (read-only).

Classification is a guide for first-pass triage and may not sort every entry correctly. It does not show whether harm occurred or what an attacker intended. The tool never sends, deletes, or edits mail, and never changes DNS.

Can you actually read your DMARC reports?

DMARC aggregate reports (RUA) arrive as XML — just source IPs, SPF/DKIM results, and counts. At a glance it's impossible to tell which rows are spoofing, which are your own misconfigurations, and which are harmless forwarded traffic.

This tool analyzes report contents and related bounce messages locally and separates what needs action from what can be ignored.

Six classification labels

Spoofing suspected

Both SPF and DKIM fail, originating from external IP. Highest priority.

Config issue

Legitimate sender failing auth. Check DNS or sending path.

Forwarded

Failure caused by forwarding. Usually no action needed.

Legitimate

Pass. Kept for record.

Bounce

Correlated with matched bounce messages.

Unknown

Insufficient information for automatic classification.

Classification is done by a rule-based engine. No AI inference or cloud analysis is used.
